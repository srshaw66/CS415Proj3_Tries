Implementing Auto-complete Using Tries

Given a query string q, the goal is to output all strings that have q as a prefix.

For example, if our Trie contains:

foo, food, fun, funky, funny

and the query string q is fo, the output should be:

foo, food

Similarly, if q is fun, the output should be:

fun, funky, funny

You will implement two versions of a Trie and use both to generate auto-complete results:

  1. A standard array-based Trie.
  2. A memory-optimized BST-based Trie.

The purpose of this assignment is not only to implement both data structures, but also to analyze the trade-off between their time and space requirements.

Gen AI Guidelines

This assignment is intended to assess your ability to design, implement, test, and analyze Trie data structures. Because code-generation tools are readily available, the following rules apply.

You may use Gen AI tools for:

  • Conceptual explanations of Tries, BSTs, and Ternary Search Trees
  • High-level design discussions such as a class structure [this means function prototypes, class design, etc., typically found in a header file]
  • Pseudocode for data structures and/or algorithms.
  • Explanations of time and space complexity.
  • Suggestions for test cases or search keys.

You may not use Gen AI tools to:

  • Convert pseudocode into implementation code.
  • Implement the methods, functions, or algorithms 
  • Rewrite, debug, optimize, or substantially modify your code.
  • Generate the input-processing, string-cleaning, Trie, BST, search, auto-complete, or reporting portions of the project.
  • Use code-completion tools such as GitHub Copilot or similar programming assistants.

 

Memory constraints

A disadvantage of an array-based Trie is that it is very space-hungry. How can we make it more space-efficient, at the cost of additional search time?

Instead of using a Trie node containing 26 pointers, store pointers only for characters that are actually present. These character pointers are organized using a Binary Search Tree (BST).

For example, if a Trie node has eight non-NULL child pointers in the standard implementation, the memory-optimized version stores only those eight characters in its BST representation.

The disadvantage is that it may now take several comparisons to determine whether a character is present. In the standard Trie, a character can be found using one array access. In the BST-based version, the search may require multiple character comparisons.

In this assignment, we will refer to this structure as a BST-based Trie. This representation is also called a Ternary Search Tree, because each node has three pointers:

  • A left pointer.
  • A middle/equal pointer to the next character in the word.
  • A right pointer.

You can create your own Ternary Search Tree here: https://www.cs.usfca.edu/~galles/visualization/TST.htmlLinks to an external site.

Here is a Ternary Search Tree for strings: {cute, cubs, cube, cup, cot, cya, act, acted, day, daze} obtained using the above visualization: Example of a ternary search treeDownload Example of a ternary search tree  

 

Implementation Details

  • Implement both the standard Trie and the memory-optimized BST version.
  • For each Trie, compare and analyze the (NOTE: time refers to the number of basic operations, not the actual time taken):
    1. Time and space taken to build the Trie (cases 1 and 2 in the sample output below)
    2. Time taken to search for a query string (case 1 in the sample output below)
    3. Time taken to output the autocomplete results for a query string, including the time required to locate the query string (case 1 in the sample output below). 
    4. Time taken to search all the strings in a file (case 2 in the sample output below). Note: For each string in the file, the search starts from the beginning (from the root of the Trie). 

Time = operation count

Use the following model consistently to measure time (some of these are relevant during Trie construction, some during search, and some during both!):

  • In the standard Trie, inspecting the appropriate array position counts as one child lookup.
  • In the BST-based Trie, each character comparison with a BST node counts as one child lookup.
  • Creating a new Trie or BST node counts as one operation.
  • Assigning a new pointer counts as one operation.
  • Checking or updating a word-ending marker counts as one operation.
  • During auto-complete traversal, count every child representation inspected.
    • For the standard Trie, this includes the array positions examined, including NULL positions.
    • For the BST-based Trie, this includes the BST child nodes inspected while traversing the available children.

Space = Trie Nodes in Pointer Units

Let NT be the number of Trie nodes, including the root.

Each node contains:

  • 26 child pointers.
  • A word-ending marker.
  • Possibly other bookkeeping fields.

The primary pointer-based measurement is:

Sstandard=26NT

pointer units.

Let NTST be the number of TST nodes.

Each TST node generally contains:

  • A left pointer.
  • A middle/equal pointer.
  • A right pointer.
  • A character field.
  • A word-ending marker.

The pointer-based measurement is therefore:

STST=3NTST

pointer units.

Note: comparing only 26NT with 3NTST is useful for illustrating the pointer-layout trade-off, but it is not a complete byte-for-byte memory comparison.

Input normalization

Your code must convert all input strings to lowercase and ignore punctuation and special characters.

Examples:

People,       becomes people
America:      becomes america
seventy-five  becomes seventyfive
to-morrow     becomes tomorrow

Double dashes are also ignored. Therefore:

rest--along   becomes restalong

This may distort the meaning of some words, but it simplifies the implementation.

Command-Line Interface and Sample Output

Your executable must accept:

  1. The input filename.
  2. A flag indicating whether a specific string or all strings should be searched.

The flags have the following meanings:

  • flag = 1: Search for specific query strings and compute auto-complete results, using both Tries.
  • flag = 2: Search for all strings in the file, using both Tries. Do NOT compute or display auto-complete results.

Case 1 (flag = 1)

  1. Build both Tries.
    1. Report the operation count and space occupied for each Trie.
  2. Prompt and search for multiple query strings (Ctrl-C to quit).
    1. Report the search operation count for each Trie.
    2. Produce and display the auto-complete results for each Trie.
    3. Report the total operation count required to produce the auto-complete results.
./a.out test2.txt 1

Report Requirements

Submit a report that contains all information necessary to evaluate your implementation and analysis. The report is the primary grading document. Your code will be submitted separately and may be run to verify the results reported in the document.

The report will have the following components:

  • Results corresponding to both cases 1 and 2
  • Space and time complexity comparison
  • Reflection and Analysis

The report must be complete enough that the implementation can be graded primarily from the document. Missing operation counts, missing auto-complete results, or unsupported conclusions will result in lost credit even if the program itself runs correctly.

Use this report template to provide your analyses: P3_reportTemplate.docxDownload P3_reportTemplate.docx
